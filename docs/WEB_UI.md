# WEB_UI — BeeAgent Operator Console

## Purpose and ownership

BeeAgent serves its canonical Web console through the BeeUI-backed `src/beeagent_module/interfaces/ui/` implementation. BeeUI provides generic rendering, session UX and components; BeeAgent owns product read models, server-side resource authorization, approved integration callbacks and narrowly scoped write actions. The older `src/beeagent_module/web/` package remains legacy and is not the target for new UI work.

This document describes the current Web and JSON contracts. [SECURITY.md](SECURITY.md) defines policy; [DEV_GUIDE.md](DEV_GUIDE.md) covers startup; [product/ui_roadmap.md](product/ui_roadmap.md) tracks future work.

| Concern                                                                   | Owner                                                                                               |

GET/read-model fallbacks never modify storage. UI view state and read-model artifacts are not sources of authority for CRM actions, mailbox execution or security-scanner permissions.

## Authentication and access control

`web.auth` in `config/settings.yml` configures `beeui_session` mode, the `session_secret_env` reference and named principals. Each local principal has an `id`, `username`, `role` (`viewer`, `operator`, `admin`), explicit resource `scopes` and an environment-backed `token_env`.

- Authentication binds the exact configured username/token pair to the canonical principal ID; roles control authority and scopes control resource access. `admin` with `scopes: ["*"]` is the global wildcard exception. Other principals must have explicitly authorized scopes; unknown resources are denied by default.
- Common scopes are `dashboard`, `rop`, `runs` and `modules`; the additional `rop.sources.write` capability grants the protected source/credential-management surface to authorized ROP operators. `rop` alone does not grant general config or mailbox credential editing.
- A principal limited to `rop` may use ROP pages and ROP-owned allowlisted artifacts but not unrelated run/module/dashboard data. Navigation is filtered, but all HTML, JSON and artifact requests are checked again on the server.
- When enabled, unauthenticated HTML redirects to `/auth/login`; unauthenticated JSON returns `401` with `unauthenticated`; authenticated but unauthorized requests return `403` with `forbidden`.
- Signed `beeui_session` cookies are managed by BeeUI. Session secrets and principal tokens live in environment, not YAML or response payloads; rotation requires reauthentication/restart as documented by the CLI. Different principals resolving to the same token are rejected.
- Disabled auth is for protected local development only, not public network exposure. Generic unknown/future paths under an enabled auth boundary remain protected.

Useful operator commands:

```bash
./start.sh auth rotate <principal-id-or-username>
./start.sh auth rotate all --logout-all
./start.sh auth rotate session
```

Public/independently authenticated boundaries are restricted to sanitized `/health`, `/static/*`, the BeeUI `/auth/*` flow, Bitrix Local Application callbacks and configured widget/event APIs. Public route status does not mean anonymous data access: widget and robot endpoints require their own separate authentication.

## ROP projection and tabs

`/rop` uses a BeeUI product adapter and canonical server-side query parameters. Tabs are `overview`, `queue`, `sources` and `blacklist`. UI supports English and Russian (`?lang=en|ru`); a valid explicit query value takes precedence over the `beeui_lang` cookie and `config/beeui.yml` default.

The overview is a bounded materialized read model: KPIs, source health and contribution, classification, deterministic recommendations, attention queues, attachments, thread context and Bitrix evidence. Explicit period selection includes `today`, `yesterday`, `7d`, `30d`, `90d`, `365d` and `all`. Aggregated period views must preserve origin-run identity, avoid cross-run duplicate inflation and distinguish missing/malformed projections from confirmed zero values.

ROP final-decision projections distinguish deterministic, AI-assisted and fallback sources. They preserve `final_case_type`, `final_case_subtype`, `final_queue`, `final_action`, `final_decision_source`, `final_confidence`, attention/reason fields and explicit `automation_allowed`/`bitrix_write_allowed` flags where supported. These fields are operator information, not authorization to mutate Bitrix. Missing legacy optional fields degrade safely. The final decisions artifact is preferred; safe read-only fallback from existing classified/adjudication artifacts is permitted without writing storage.

ROP Event Detail uses exact `run_id` plus optional `event_instance_id` to disambiguate repeated transport `event_id` occurrences. Original e-mail and document contents are never emitted as arbitrary HTML, JSON or inline attachments. Malformed or inaccessible event artifacts return bounded errors, not unfiltered raw bytes.

## Queue query contract

The Queue tab is one BeeUI `data_table` with canonical toolbar and progressive GET navigation. The server remains authoritative for filtering, sorting, pagination and output.

| Parameter                         | Meaning / supported values                                                                               |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `q`                               | Sender/subject search; `sender` and `subject` are legacy filters                                         |
| `case_type`                       | Classification filter; `classification` is a legacy alias                                                |
| `priority`                        | `low`, `medium`, `high`, `critical`                                                                      |
| `bitrix_status`                   | Supported reconciliation statuses                                                                        |
| `is_fallback`                     | Exact `true` or `false`                                                                                  |
| `queue`                           | `high_priority`, `needs_review`, `lost_in_bitrix`, `ambiguous`, `degraded`, `unreconciled`               |
| `date_from`, `date_to`            | Inclusive ISO `YYYY-MM-DD`, ordered when both supplied                                                   |
| `page`                            | One-based positive integer, default `1`                                                                  |
| `page_size`                       | `25`, `50` or `100`, default `25`                                                                        |
| `sort`                            | `received_at`, `date`, `event_date`, `sender`, `subject`, `case_type`, `priority`, `bitrix_status`       |
| `order`                           | `asc` or `desc`; default is `received_at` / `desc`                                                       |
| `columns`                         | Allowed visible column keys (`priority`, `client`, `subject`, `date`, `classification`, `bitrix_status`) |
| `run_id`, `tab`, `period`, `lang` | Canonical context preserved across valid navigation                                                      |

`sort` and `order` travel as a pair or are both omitted for the default. Invalid filter, date, enum, column, page or sort values must be refused rather than broadening the result. The table ID is `rop-queue`; only this table receives the ROP-specific toolbar. Its date picker submits on select/clear, text search uses GET, dropdown state and selected columns survive navigation, and Reset preserves context. Legacy UI-only query flags must not become independent permission or filtering rules.

Missing/invalid event dates sort after valid timestamps in both directions. Attention events are bounded (existing cap `500`); the UI cannot request unbounded underlying storage.

## Protected ROP writes

Normal GET routes remain read-only. The following explicit bounded actions are exceptions; they use the existing BeeUI action/CSRF boundary, validated inputs, server-side role _and_ scope checks, and audit.

### Sender blacklist

`/rop?tab=blacklist` supports protected Add/Update/Delete for an exact sender e-mail key, with name/title and a bounded business reason. Search, pagination and CSV export are read-only; CSV import is not supported. Blacklist decisions can affect subsequent ROP classification (`irrelevant`) but do not edit historic source artifacts or perform CRM mutations.

Bitrix robot callback endpoints `POST /api/bitrix/rop/events` and `POST /api/bitrix/rop/events/{callback_secret}` authenticate independently using the configured application-token or constrained path-secret mode. The host re-reads the configured stage, sender and required classification field through the read-only Bitrix client before a canonical idempotent blacklist mutation. A callback never trusts unverified event text as an action. The path secret must not appear in reverse-proxy access logs, redirect URLs, responses or query strings.

### Sources management

The Sources tab reads the canonical configured source registry and a bounded materialized all-time contribution projection. `Processed total` is zero only when a valid projection confirms that the source contributes no events; missing/malformed projections are unavailable. `Available sources` counts enabled sources with a successful latest connection check, not indefinitely open sockets.

Authorized Add/Edit/Delete, Enable/Disable and mailbox Check require `operator` or `admin`, `rop` and `rop.sources.write` (or the admin wildcard). Mailbox Check performs only connect, login and read-only folder select, storing safe connection health under `storage/interfaces/rop_source_connection_health.json`.

The credential-management path may update only the selected mailbox source's username/password environment references. Mailbox passwords never enter YAML, returned APIs, CSV or audit; when editing, a blank password preserves the current value. An authorized manager may view the username, but passwords are rendered only as a presence mask. No Sources action grants Dashboard, arbitrary settings, global auth, `rop run` or CRM write-back authority.

## BeeScan investigation workspace

`/beescan` is a standard adapter-backed BeeUI page with persistent security conversations, owned Case history, protected context controls and independent investigation runs. A single Send routes ordinary questions to Ask and clear active-assessment requests through bounded intent classification and the existing governed investigation. Intent classification grants no execution authority. BeeUI owns rendering, locale/theme, generic forms, chips, native file selection and polling. BeeAgent owns Case state, current resource permissions, authority, provider calls, attachments and execution. Historical investigation Cases retain their existing Start/Resume, evidence, review and report contracts.

### Persistent conversation contract

New parent identities use `web-chat-…`. The conversational UI submits `beescan_send` with `nonce`, `message` and `mode`; existing Cases also require `case_id` and `revision`. Ordinary questions, including questions with a saved Target, use Ask with zero target requests. Clear direct active requests require an independently validated `Investigate` classification from the configured AI runtime; ambiguous, malformed or unavailable classification falls back to Ask. Missing Target, policy authorization, an approved two-principal profile or an expired test session produces concise RU/EN prerequisite guidance through the existing `+` actions and zero target requests. Actor, current approval, exact origin, capability eligibility, hard budgets and ManagedEgress remain authoritative. The chat message supplies the complete objective; this flow has no second Task field or typed confirmation. `beescan_conversation_create` accepts `nonce`, `message` and optional `mode`, creates an owned Ask-only Case and persists the question before contacting the provider. Ask requires an authenticated operator/admin with BeeScan resource access; it does not require Target, investigation permission or target approval. `beescan_ask` accepts `case_id`, `revision`, `nonce`, `message` and optional `mode`; mode updates only the next-run preference and never starts execution; configured-provider failure preserves the question and shows a localized configuration, provider-refusal or temporary-response state. Conversation Ask/intent requests to the selected OpenRouter profile disable reasoning within the existing token budget and use strict JSON Schema; neither model selection nor execution limits are widened. Safe diagnostics contain an allowlisted category and HTTP status only, without prompts, response bodies or credentials. Provider input contains at most twelve recent messages within 6000 text characters and bounded facts from up to three previously authenticated child results. Credentials, private screenshots, raw attachments and HTTP bodies are excluded; operator observations do not become authenticated proof or execution instructions.

`conversation-NNNNNNNN.json` records are append-only, HMAC-authenticated and chained to the preceding record. Entries retain stable identity, sender, host timestamp, type, actor and source reference. The authenticated `conversation_head.json` control pointer detects missing/truncated tails; prior evidence records are never overwritten. An exclusive Case lock and expected revision reject conflicting writes. Mutation nonces bind the operator, exact parent Case and revision, expire after ten minutes and are consumed in the signed ledger. Each record is bounded to 64 KiB and a Case accepts at most 10,000 records; limits fail explicitly without discarding persisted messages. `message_page` selects eight-message pages and `run_page` selects 25-run pages; omitted selectors show the latest page.

`beescan_context` accepts the common `case_id`, `revision`, `nonce` plus `key`, `value`. Supported keys are `target`, `scope`, `authority`, `profile`, `principal`, `observation`, `mode`; an empty value removes a context entry. Bearer/Cookie references support removal only through this action; plaintext values are accepted exclusively by the protected session intake. Target is an exact HTTP(S) origin saved as non-authoritative Case data without target requests. Saving a syntactically valid local/private/excluded origin does not authorize execution; the UI explicitly distinguishes retained data from a host-policy HTTP prohibition. Invalid origin, changed revision and expired action receive separate safe error categories, not a universal stale-state message. Under server-managed target policy, Scope and authority references derive from the stable parent Case; legacy static policy requires its exact configured scope/mission references. A configured profile must belong to the operator and Target. Context revisions are monotonic and carry signed mutation provenance. Target, Scope, authority or principal changes clear current credential references; historical snapshots remain intact.

`beescan_session` adds `kind` (`bearer` or `cookie`) and write-only `secret` to the common mutation fields. Target, Scope, authority and an independently identified test principal must already exist. The host retains the bounded plaintext only in process memory for ten minutes, bound to operator, Case, origin and context identity; records contain opaque references only. Duplicate active bindings, malformed values, expiry and foreign identities refuse. Removal discards the current secret; restart restores metadata but requires re-entry. Only one attached session may be selected for a run. Session-backed execution narrows the existing workflow to approved same-origin read-only requests, uses sealed anonymous memory descriptors and refuses redirects; it disables active DAST and cannot establish IDOR findings. Existing configured two-principal Bearer profiles remain available through their separate governed comparison contract.

The compatibility action `beescan_investigate` accepts the common mutation fields plus `task`, `mode` (`quick`, `standard`, `deep`) and exact `confirmation: INVESTIGATE`. It reauthorizes the current operator, module, capability, Target and scope, then creates an independent existing investigation child under the persistent parent. Signed parent records and child ownership bind an immutable context/attachment snapshot and authority digest. An active child prevents another concurrent investigation; Ask and context edits remain available. PARTIAL/ERROR/REFUSED and terminal results permit subsequent questions and independently authorized new objectives. Child evidence, Finding identities, Review and Report packages remain unchanged; child links open the existing protected results workflow. Legacy checkpoint Resume continues to require its original immutable objective and authority.

`beescan_attach` is registered through BeeUI's fixed protected multipart action endpoint. It requires the same Case/revision-bound nonce, operator ownership and header CSRF. TXT/MD/JSON/HAR/PNG/JPEG are limited to 2 MiB each, eight attachments and 16 MiB input bytes per Case. Filenames never select paths. Restricted local validation bounds structure, normalized file size, image dimensions (4096 pixels per side) and decompression (64 MiB). PNG intake supports 8-bit non-interlaced grayscale/RGB/alpha screenshots and JPEG intake supports one- or three-channel frames. Publication requires successful attachment-store read-back. HAR persistence keeps only request method/origin and response status; headers, cookies, credentials, body, path/query material and response text are discarded. The existing host attachment store retains sanitized observations and private screenshots under opaque IDs; none are automatically AI-visible or treated as authenticated evidence. `beescan_attachment_remove` accepts a Case-owned `storage_run` reference and appends a removal record, preserving historical bytes and snapshots.

The central rounded composer remains active after terminal results. Its bottom toolbar contains `+` on the left and one effort selector immediately before the upward-arrow Send button. `+` is available before any message: the first protected Target/observation mutation or valid file intake creates an owned empty Case through the existing create boundary; merely opening or cancelling a dialog creates nothing. Target intake derives Scope and authority references from the current host policy when available, never from an AI assertion. Compact Tabler dialogs offer Target, testing authorization when necessary, grouped approved profile/principal/Bearer/Cookie access and native file selection. An ordinary operator message is stored once as a bounded signed untrusted operator note; it remains available in bounded Ask history without a duplicate observation field or a mandatory observation form. The observation context action remains compatible for existing callers. Anonymous authorized investigations and public Ask do not require credentials; two-principal checks still require an approved comparison profile. `beescan_access` accepts `principal`, `profile`, `kind` (`none`, `bearer`, `cookie`) and write-only `secret` with common mutation fields; profile plus attached session is refused. Chips support explicit edits/removal and credential re-entry state; derived authorization identifiers and effort are not duplicated as ordinary chips. A compact conditional right summary appears only when Target or child runs exist. Initial layout and read-only polling use the same optional context shape, including empty detail defaults. The summary uses owner-checked inspect projections for current status, latest-25 completed/active counts, measured request/time data and authenticated Findings/CANDIDATE counts; each child links to its existing Results/Review/Report/Export workflow. Unauthenticated evidence never supplies finding counts or fabricated measurements. An empty Ask-only Case has no panel. On mobile the summary uses the existing alternate-panel control. Conversation messages suppress author/type metadata and display localized date/time in the browser timezone while retaining the original ISO UTC timestamp in data and signed records. Quick/Standard/Deep uses a canonical Tabler dropdown inside the composer. Every owned history row has protected rename and remove-from-list dialogs. Removal archives signed metadata and preserves all evidence, refuses an active Case, and opens a new conversation when removing the selected Case. New history actions include a short-lived actor/Case/current-metadata-bound nonce; changed metadata or replay refuses. Historical action payloads remain compatible. RU/EN, light/dark, desktop/mobile and generic BeeUI route-prefix/embedded behavior remain supported. `GET /api/beescan/status?run_id=<parent-or-child>` is read-only; parent responses contain bounded messages, non-secret context, paged child references and safe presentation metadata. Ordinary reads, Ask and offline Review/Report/Export create zero target HTTP requests.

Conversation run entries display compact execution cards when the host can bind them to signed sources. Discovery and each completed provider invocation use separate identities in saved order. An execution status describes the provider lifecycle. A verification outcome describes its evidence and does not promote a Finding. Exact check totals can drive progress, while active work with an unknown total uses indeterminate progress. A budget is displayed as a limit. The overall investigation result has a separate card linking to Results. Historical records without authenticated details use an unavailable state for those details. The Case sidebar uses authenticated request accounting and verified execution identities. Finding review disposition and severity use the published finding metadata. Polling preserves the page locale through optional `lang` (`en` or `ru`) on the status route. The summary shows authenticated High, Medium and Low finding counts when complete; the existing Results route accepts an optional `severity` allowlist and shows only matching authenticated findings. The saved Case can link to a filtered child result without changing Review or Report authority. New investigations start from New Case. The Inspector shows an empty Logs section when no authenticated log was saved.

`GET /api/beescan/execution` requires the conversation `case_id`, its `run_id` and the projected `execution_id`, plus optional `lang` (`en` or `ru`). Every read checks current BeeScan principal access, the signed conversation and its run binding, and the signed Case receipt and child evidence for completed executions. The Inspector returns a bounded projection of known times, counters, provider/profile IDs, allowlisted diagnostics and evidence references. Where verified evidence includes HTTP response counts, the Inspector displays totals by status code. Verified comparative checks also expose a bounded table of HTTP status, recorded oracle signal and control role. The Case panel can focus the existing protected composer action when available. It shows an empty log section when there are no safe saved log entries. Before terminal evidence is available, the host publishes signed lifecycle observations for the Web run and each started execution with the same identities used by the receipt. Child ownership is checked on every read. Lifecycle observations contain status and available timing and action identities. Evidence, counters and outcomes require the authenticated receipt. After restart, a previously running execution without a live worker or terminal receipt is shown as unavailable. Inspection does not load arbitrary artifacts or execute Target requests.

### Historical investigation compatibility


Coordinated development uses the existing editable BeeUI checkout at `../beeui`. Deployment requires a reviewed BeeUI distribution containing `chat_workspace`; the editable integration is not release-source verification. Release BeeUI first, then update BeeAgent’s actual PyPI pin and corresponding lockfile through the approved dependency handoff and rerun release-source regressions before merging the BeeAgent integration. Package versions are not changed during this implementation.

Start and Resume use the existing CSRF-protected `POST /api/actions/execute` with action IDs `beescan_start` and `beescan_resume`. Execution requires the verified session's operator/admin role, `beescan.investigate` plus `beescan` (or admin wildcard), explicit membership in `beescan.investigation.web.principal_ids`, and current server execution policy. The optional `web` configuration is disabled when absent; when present it must contain exactly `enabled` and `principal_ids`. Enabled Web execution additionally requires enabled Web authentication, enabled investigation and configured general discovery limits. With `beescan.target_policy`, the host derives bounded per-run approval from Target, current exclusions and a pinned public DNS destination; no target-specific YAML approval is required. Configurations without this section retain legacy static approval behavior. Invalid configuration fails validation. See the [operator setup](product/beescan_guide.md#web-investigation-setup).

The forms submit `target`, `task`, `mode`, a short-lived principal-bound nonce and, when selecting an approved authenticated comparison, `test_profile_id`; Resume additionally requires `case_id`. Authority, provider, budget and actor overrides are rejected. Nonces expire after ten minutes and each accepted action consumes its identity durably. One Web invocation may execute per storage root at a time; concurrent requests refuse rather than queue duplicate scans. The accepted response returns the durable Case/run identity while the existing investigation executes. Refresh or polling reads the saved progress, steps, request count, elapsed time, evidence references, candidate Findings and safe report projection. Token/cost availability remains explicit. A preview returns only `execution_authorized: false`; it does not inspect protected resources or grant authority. Target-policy refusal publishes only a private signed intake/status run with state `REFUSED`, a bounded reason and zero target requests; the action returns that run ID so the existing workspace can show the reason. It does not create a completed assessment or enable review/report preparation.

Quick/Standard/Deep cap general steps/requests/depth at `2/2/1`, `8/8/3` and `16/20/4`, respectively, further restricted by configured host ceilings. They do not grant new capabilities. Server-managed Web DAST uses the enabled existing nonrecursive profile and authenticated discovery, with per-run transport approval and the existing provider, destination, budget, mediation and cleanup checks. Legacy configured approval and CLI contracts remain compatible. The nonrecursive verification profile requires Standard or Deep; Quick refuses before execution. Exact-entry DAST and protected terminal disclosure are not Web presentations.

Legacy investigation Cases retain bounded original Target/Task/mode in host-signed `web_intake.json`, bound to the existing ownership identity. This is input metadata, not a conversation database or execution authority. The chat reconstructs the operator request and ordered host events from this metadata and authenticated Case segments; it invents no timestamps, progress percentage, explanations or usage measurements. The status projection is bounded to 64 KiB, retaining at most 64 host events plus bounded candidate findings. Missing measurements remain unavailable. Historical Web Cases without authenticated intake remain inspectable but automatic Resume is unavailable. Altered intake or completed checkpoint authentication fails closed.

After Start, the browser opens the returned run in the same Case conversation and polls only the authorized status endpoint every three seconds, bounded to 300 attempts. Polling stops on authenticated completion, terminal ERROR/REFUSED/TIMEOUT or repeated failure and aborts on page exit. Terminal failure stops progress presentation even when evidence authentication is unavailable; it does not authenticate evidence or create a Finding. Resume submits the saved original Target, Task and mode using the existing protected action; the composer is read-only for an existing Case. A different objective requires New Case. Polling replaces events by stable host identities, without appending duplicates or treating presentation state as evidence. Generic templates and browser assets are packaged by BeeUI; BeeAgent has no custom BeeScan HTML renderer, frontend bundle or static mount. The composer reuses BeeUI’s existing protected action/CSRF transport. The authorized status response adds bounded `presentation` metadata for generic messages, state, bounded read-only Context sections and compatible existing KPI value updates; authenticated completion reloads the canonical page for current actions and final sections. Read conflicts during atomic publication receive at most three fresh snapshot attempts; invalid evidence and ownership still refuse.

Host-signed `web_owner.json` binds every Web Case, segment and child run to the verified principal. `web_receipt.json` authenticates completed Case/evidence/report bytes independently of the Case's existing digest. Existing Case schemas remain unchanged. Resume requires the original Target, Task, mode and unchanged approved BeeScan configuration, current permissions, a valid signed receipt and a compatible checkpoint; sufficient terminal work is reused without target traffic. Pending, foreign, unowned historical and tampered checkpoints refuse. An interrupted process is never automatically replayed.

BeeScan resources are excluded from generic Dashboard/run listings and denied through generic run/artifact routes, including for wildcard principals; use the owned workspace projection. Historical CLI Cases receive no implicit Web ownership. Raw HTTP bodies, sensitive values, query payloads, credentials, private paths and arbitrary report bytes are not exposed. Ownership signatures derive from the environment-backed Web session secret with a separate signing context; changing that secret invalidates existing Web ownership, so retain it securely when durable Case access is required.


### Independent Finding review and report export

Results offers `beescan_review` and `beescan_report_prepare` through the existing CSRF-protected product action transport. Mutations require the current operator/admin role, BeeScan resource and investigation scope (or admin wildcard), configured Web principal membership, an enabled BeeScan module and exact signed Case ownership. Offline review does not renew or execute active-scan approval. Completed authenticated DAST candidates from Case schema 3/4 and access-control candidates from schemas 5/6 qualify; the host reloads the original typed source, evidence digests and source action through the existing restoration contracts and signed Web receipt. Unowned CLI Cases remain inaccessible.

Review input contains exactly `case_id`, `finding_id`, `disposition`, `decision_basis`, `evidence_text` and `independence_attestation`. Identity and UTC decision time come from the host session. Decision basis is bounded to 512 UTF-8 bytes and evidence to 4096 UTF-8 bytes, with controls and common credential-bearing forms rejected. VERIFIED requires nonempty evidence and the exact independence attestation shown in the form. Rejected/inconclusive decisions may omit evidence. Automated artifact/request/response digests cannot substitute for independent evidence; a storage-wide immutable digest claim refuses evidence reuse. Human attestations remain attributable assertions, not objective cryptographic vulnerability proof. Raw evidence and private decision basis never appear in the workspace or exports.

Reviews are immutable in separate `wr-` runs. A second decision for the same Case/Finding refuses; no implicit supersession exists. Report preparation accepts exact Case/Finding/review identity plus the fields of BeeScan `ReportDetails`; an empty review ID creates only a candidate draft when no review record exists. Reproduction, impact and program requirements need separate explicit confirmations. The browser cannot supply a report, reviewer, VERIFIED flag, execution request, path or filename. Up to sixteen report revisions are stored as separate `vr-` runs; completing an incomplete report preserves the accepted human review and earlier reports. Existing BeeUI text fields support short prose (254 characters); the host's typed intake retains its documented larger bounds and ordered step lists.

Private artifacts use ArtifactAPI with exclusive creation, owner-checked no-follow reads, read-back, fsync and an atomically published HMAC receipt. `review_record.json` and optional `human_evidence.txt` belong to the review package; `vulnerability.json`, `vulnerability.md`, `report_details.json` and optional `submission_draft.md` belong to each report revision. The signed receipt binds file hashes, principal, original Case/Finding and source artifact hashes. Missing or interrupted publication is incomplete and cannot replace an earlier revision. Durable digest claims may remain reserved after a failed write; retries must not silently reconcile or overwrite those records.

Results shows disposition, readiness, missing information, submission eligibility, independent evidence references and an escaped report preview. `GET /api/beescan/report` requires exactly `case_id`, `finding_id`, `report_run_id`, `format` (`json`, `markdown`, or eligible `draft`) and `download` (`true` or `false`). Downloads use fixed attachment filenames, no-store, nosniff and sandbox CSP; previews return content inside a JSON envelope. Reads revalidate signed ownership, original source and package integrity without generating reports or target traffic. Guessed IDs, foreign Cases, arbitrary paths, symlinks, hardlinks, unsafe permissions and changed/oversized files refuse. Keeping the Web signing secret stable permits reopening after process restart; generic artifact routes never disclose these packages.

### Approved two-principal GET comparisons

`beescan.access_control` is optional and contains exactly `profiles`, a list of at most sixteen host-provisioned profiles; an empty list exposes no authenticated comparison option. Configuration is validated after optional domain installation during bootstrap. The browser selects only a profile ID, never credentials, account IDs, roles, resource permissions or proof assertions. Legacy comparisons require Standard/Deep and at least eight effective request and step slots; autonomous limits are described below. Public execution requires HTTPS and the existing public-target policy; a private laboratory additionally requires explicit `local_lab_enabled`, matching static transport approval and `allow_private_lab`, without changing public destination policy.

Each legacy explicit-resource profile requires `profile_id`, exact canonical `origin`, `operator_ids`, aware ISO `valid_from`/`expires_at`, opaque `authorization_reference`, exactly two `principals`, one `resource`, `relationship` (`horizontal` or `vertical`), `request_budget: 8`, `seconds` (1–60), `read_only: true` and explicit `local_lab`. Each principal requires distinct `principal_id`, `credential_env`, `account_id` and `object_id`, plus `role`, `identity_path`, `identity_field`, `role_field`, `baseline_path` and `object_field`. The environment value is one bounded Bearer credential; cookies, arbitrary headers and login automation are unsupported. Initial/final identity JSON must match the configured account ID and role; distinct labels or token strings alone do not prove two identities.

The resource requires `resource_id`, approved observed `path`, `owner_id` matching the first principal, `object_field`, `object_id`, one to eight unique `private_fields`, explicit `expected_access` (`[true,false]`, `[true,true]` or unknown/null) and `public`. Its path/object binding must match the owner's baseline. Selectors address scalar JSON fields through at most four named object components; arrays, arbitrary scripts and inferred ownership are unsupported. Configuration contains references and expectations, never credential values or private disclosure values. Sensitive query parameters are refused; query values do not enter domain records or reports.

The existing capture worker executes only the two initial identity GETs, owner baseline, second-principal baseline, anonymous control, source-bound cross-principal GET and two final identity GETs. Credentials are passed in sealed anonymous memory descriptors, attached to one exact-origin request and never inherited from another principal or a response cookie. Redirects refuse. The host requires object-bound owner proof, private fields distinct from the second principal's own object and matching private fields in the cross response; it emits only bounded facts and opaque keyed digests. Missing owner proof prevents cross execution. Current configuration, credentials, destination and validity are rechecked throughout, with existing DNS/IP/TLS, managed egress, deadlines, accounting and cleanup enforcement. No AI receives these bodies or credentials.

Legacy explicit-resource access-control Cases use additive schema 5 with `access_control.json`, per-request redacted evidence and the existing lifecycle, owner and receipt artifacts. Historical Case schemas and vulnerability report schema 2 remain compatible. Signed intake retains `test_profile_id`; Resume requires the original profile, unchanged authority and unchanged credential bindings. Completed Cases are reused without target traffic; interrupted/unpublished checkpoints refuse. Reading completed evidence and Review/Report/Download do not require live target credentials and send no target requests. PARTIAL, REFUSED, ERROR and TIMEOUT cannot publish a candidate or complete negative result.

### Autonomous authenticated access investigation

An access profile may instead select `discovery: true`. This variant replaces the legacy `resource` and `relationship` keys with explicit `expectation` (`owned_private`, `role_restricted`, `public`, `unknown`) and `discovery_budget` (2–16 requests). Each of its exactly two principals contains only `principal_id`, expected `account_id`, approved `role` and environment-backed `credential_env`; operators supply no object IDs, vulnerable endpoints, identity paths or proof selectors. Other origin/operator/authorization/validity/read-only fields remain mandatory; `request_budget` bounds the entire investigation (1–64) and must cover the discovery budget. The first approved context supplies owned resource hypotheses; comparisons test the second context against those resources. A role-restricted expectation is an explicit operator assertion about this ordered pair, not an inferred role hierarchy.

Discovery starts with authenticated GET `/` for each context and follows only observed same-origin GET links/forms and JSON links. Bounded OpenAPI descriptions may advertise literal GET paths marked `x-readOnly: true`; unresolved path templates never generate identifiers. Supported JSON self-identity records at the root or under `identity`, `user`, `current_user` (optionally inside `data`) have an approved account identifier (`id`, `account_id`, `userId` or `sub`) and matching `role`; object records have `id`/`object_id`/`uuid`, explicit owner association (`owner_id`, `ownerId`, `user_id`, `userId` or `owner.id`), observed resource location and bounded scalar object fields. Arrays, nesting and link counts are bounded. Ownership cannot come from URL spelling. Selectors and object bindings are derived transiently from actual responses. Missing or conflicting evidence, unsupported application shapes and login pages cannot establish an authenticated hypothesis. Unknown expected permissions return `authorization_expectation_required` without cross-principal execution.

Quick allows two discovery requests and no comparative verification; Standard allows four discovery requests and at most twelve total requests; Deep allows four discovery requests and at most twenty total requests. Profile and current host request/time ceilings can only reduce these limits. The effective host step ceiling counts discovery requests and selected comparison actions; control requests remain separately accounted. Each selected comparison reuses the existing eight-control verifier, with discovery separately accounted and the original overall deadline retained. A completed negative or partial hypothesis advances to the next distinct eligible resource when budget permits. Remaining frontier, unresolved ownership, unknown visibility or exhausted budget yields PARTIAL rather than a complete negative claim. Known mutating operations, redirects, foreign origins and unsafe references refuse or are excluded.

Autonomous Cases use additive schema 6 with redacted `discovery_evidence.json`, source-bound hypotheses, separate comparison/cleanup records and explicit budgets/discovery accounting. The existing signed owner/intake/receipt authenticates all sources and comparisons. Progress distinguishes identity establishment, discovery, hypothesis selection and comparisons through existing workspace components. Restart, authorized terminal reuse and protected Review/Report/Export retain the same integrity and zero-target-request guarantees; uncredentialed ordinary discovery remains available without claiming authenticated IDOR verification. Legacy schema-5 profiles remain supported.

## Artifacts and attachments

Artifact routes accept only validated run/opaque artifact IDs and allowlisted types through BeeUI and the BeeAgent adapter. Arbitrary paths, symlinks, traversal, unknown run IDs and other modules' protected artifacts fail closed. Previews are size-bounded, escaped and redacted; inaccessible or malformed records degrade to an explicit error/warning.

`GET /rop/attachments/{attachment_id}/download?run_id=<run_id>&event_id=<event_id>` resolves only a manifest-approved original. `run_id` is required; `event_id`, when supplied, must agree with the stored item. The response is a forced attachment with `Content-Type: application/octet-stream`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. There is no inline HTML, MIME rendering, raw `.eml` or nested-message download bypass. Disabling ROP attachment semantic analysis does not bypass storage-level download authorization.

The JSON/HTML read models exclude raw e-mail messages, raw content, attachment bytes, cookies, secrets, unrestricted scanner reports and sensitive identifiers. Safe `read_only` response metadata cannot substitute for route-level security checks.

## Bitrix integrations

### Widget API

`GET /api/bitrix/rop/widget`, `/events` and `/events/{event_id}` are bounded, read-only projections. When enabled, they use a dedicated configured Bearer token through `bitrix.widget.token_env` and `bitrix.widget` limits/periods. The output includes safe final-decision summaries and bounded event identities. It never triggers mailbox processing, CRM writes or runtime capabilities. The widget token is separate from a BeeUI session and from Local Application OAuth tokens.

### Embedded Local Application

The ROP console can be opened inside the configured Bitrix24 portal as a server-side Local Application with UI. `bitrix.embedded_app.enabled` requires Web auth. `portal_origin` is the exact trusted HTTPS origin; it controls both outbound Bitrix REST calls and CSP `frame-ancestors`. An embedded session uses `HttpOnly`, `Secure`, `SameSite=None` and a constrained age. Its assigned role is the configured `viewer` or trusted-audience `operator`, never a browser-selected role or `admin`.

- `POST /bitrix/rop/install` validates bounded form fields, current Bitrix user and token expiry, then atomically binds one `member_id` to the configured portal in `storage/interfaces/bitrix_rop_app.json`. A foreign installation/portal is rejected. Installation may also start the first valid ROP session.
- `POST /bitrix/rop/launch` validates the existing binding and current user with `user.current` against **the configured portal**, then issues the restricted BeeUI session and redirects `303` to `/rop`. `GET` launch is not a credential transport. Bitrix requires the `user` application permission.
- Actual Bitrix payloads may omit `DOMAIN`; the trusted domain always comes from `portal_origin`. Any supplied `DOMAIN` must match it. `AUTH_ID`, `AUTH_EXPIRES`, `REFRESH_ID` and additional placement data are bounded and never persisted/logged as OAuth credentials or used to create outbound destinations.
- Both handlers require an actual HTTPS ASGI request scheme from a trusted reverse proxy, not an untrusted client `X-Forwarded-Proto` header. OAuth credentials never enter URLs or rendered HTML. Sessions and responses use `no-store` and `Referrer-Policy: no-referrer` where appropriate.

The local `/auth/login` flow and widget Bearer API remain independently supported. Local Application launch alone does not grant arbitrary resource scopes, CRM write-back or other execution authority.

## Non-goals and verification

The Web interface is not a generic module executor, arbitrary artifact browser, CRM administration interface, database admin, mail parser or public security-scanner console. No GET route may trigger external mutation. Additional protected actions require an explicit reviewed contract and testable server-side authorization.

For Web changes, verify the actual route and method, authentication and resource scopes, CSRF on mutation, invalid inputs, pagination/filtering, redaction, download headers, compatibility with old run artifacts and absence of unintended writes. Use `tests/test_web_console.py`, `tests/test_rop_web_projection.py`, `tests/test_bitrix_embed.py` and relevant integration tests. Only claim test/CI success when run and observed.
