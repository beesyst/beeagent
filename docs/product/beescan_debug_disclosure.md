# BeeScan BS-10 diagnostic disclosure

A reviewed Git installation is supported both in production and in an explicitly authorized controlled Linux laboratory. Laboratory mode validates the current policy, private-target permission and allowed destination before applying the same project requirement, locked Git revision, installed version/commit and module-origin checks as production. The debug laboratory status remains `LABORATORY_ONLY`; a valid Git production run uses `COMPLETE`. Laboratory permission never substitutes for dependency provenance.

BS-10 supports the exact `/home/bee/Pro/beescan` editable installation for the trusted local operator CLI. An authorized global destination uses the explicit `LOCAL_EDITABLE` integration status after the existing private `_LocalRun`, current policy, exact source declaration, installed editable metadata and module-path checks. Private destinations still require the existing explicitly enabled private laboratory mode and remain `LABORATORY_ONLY`. Neither editable mode is immutable production `COMPLETE`. Git production dependencies retain their existing immutable provenance validation; local editable execution does not establish a reviewed production revision or close live acceptance gates.

When the BeeScan extra is selected and project metadata declares exactly `beescan = { path = "../beescan", editable = true }`, normal bootstrap first completes its existing frozen sync, verifies that the sibling resolves to `/home/bee/Pro/beescan`, then installs that editable source offline without dependencies into the current Python environment. Installation failure stops bootstrap. Successful installation processes the current environment's site-packages so the same bootstrap process can import the newly installed editable package before contract validation. This preserves the selected local source despite a stale frozen Git installation, without changing the lockfile, operator settings or Git production installation behavior; execution still requires all existing provenance and authority checks.

The three existing input modes remain available. The operator may name one standalone uppercase configuration identifier directly in the task, for example `Find the debug page exposed by the website and identify the SECRET_KEY disclosed in its response`. This bounded lexical form accepts one `[A-Z_][A-Z0-9_]{1,63}` token, with optional surrounding quotation/backticks or sentence punctuation; absent, repeated, malformed or multiple candidates fail closed. The existing explicit `field=IDENTIFIER` syntax remains authoritative and case-sensitive, accepting `[A-Za-z_][A-Za-z0-9_]{0,63}`. It can disambiguate tasks containing other uppercase words. Both forms are parsed deterministically from the original operator task only; AI returns only the task family and cannot choose a field, path, method or authority. Do not place actual secret values in tasks or command arguments.

```bash
./start.sh beescan
./start.sh beescan investigate --target https://authorized.example --task 'Find the diagnostic disclosure field=APP_TOKEN'
./start.sh beescan investigate TASK.json
```

The placeholder target grants no authorization. Interactive/direct mode uses the existing `trusted_local_enabled` OS-operator boundary. File mode retains its existing independent `enabled`/`approval` and exact target comparison. Its terminal presentation additionally requires `trusted_local_enabled` and the actual local CLI operator context. No mode rewrites settings. Existing approval is a three-request GET ceiling; the immutable debug domain intent narrows it to at most two requests, with no baseline/mutation requests. The actual chosen family and effective two-request budget are recorded in local execution provenance.

The existing governed engine performs GET `/`, then asks BeeScan's public API to select exactly one diagnostic resource from bounded HTML comments. It performs at most one further same-origin GET. Ordinary hyperlinks, absent/ambiguous resources, unsafe URLs, traversal and query-bearing diagnostic references cannot produce a second request. The host retains the existing exact IP/port, DNS, TLS, no-redirect, attempt marker, namespace/firewall, process limits, deadlines, settings reload and cleanup checks. BeeScan determines the requested field/value association and CANDIDATE status; the host contains no duplicate field-disclosure rules. Unsupported and ambiguous classifications have the explicit `unsupported_investigation_task` terminal reason with zero target captures.

An HTTP 404 response with an unsupported `application/json` media type is refused with the fixed reason `response_json_status_404`; the body and header values are not included in that diagnostic. This reason does not establish a disclosure or identify why the resource returned 404.

For this family, both discovery and diagnostic bodies remain transient. Before any source persistence the host constructs `debug-redacted-v1`: allowlisted parent/child/request/response IDs, dependency provenance, metadata-only WebResponseFacts, projection name and a run-private HMAC over the authenticated capture plus its request/response/evidence identity. Raw capture, body, comments, diagnostic values, links and excerpts never enter the child record. The key is random process memory, never persisted; the tag binds the original capture during this run without publishing a reusable plaintext digest for guessing values. After the run it is an opaque provenance commitment, not a portable independently verifiable signature. Source snapshots and exact read-back comparisons remain mandatory throughout handoff and publication.

Parent status/result/steps/sources, child capture_status/source and JSON/Markdown reports retain bounded private ArtifactAPI storage. The new projection is additive and used only for debug investigations; the existing framework-version source contract is preserved. Debug response bodies and sensitive values are never supplied to AI. Debug uses only the classification call, with deterministic redacted reporting and no AI explanation call.

Exact value presentation happens after source authentication, managed-egress cleanup with reaped processes, final report/status publication, read-back and current authorization verification. It requires all three standard descriptors to be TTYs for the same device, an owner-matching no-follow terminal descriptor, the foreground controlling process group and a still-valid private local operator context. The value is written directly to that terminal; ordinary stdout JSON and reports never contain it. Non-TTY, redirection, background terminal use, failure, cancellation, unverifiable sources, failed publication or cleanup suppress the value. A safe MATCH can still be reported without a terminal disclosure. Terminal recording, scrollback, screen capture, same-account debugging and other OS-level observation remain operator trust risks; this boundary does not claim to prevent them. Python process memory is not guaranteed to be securely erased.

The offline grammar and limits are specified in BeeScan `docs/DATA_MODEL.md`. Unsupported or malformed formats never imply a successful disclosure. NO_MATCH covers only the requested bounded representation and is not proof that the target has no other exposures. Findings remain CANDIDATE.

Use `PYTHONPATH=.:src` for integration test imports. Local laboratory results do not replace fresh authorized PortSwigger acceptance, independent review or hosted CI gates.
