# BeeScan BS-11 adaptive investigation

The existing trusted-local CLI supports a bounded evidence-driven mode using BeeScan It12. Enable `beescan.investigation.adaptive.enabled` explicitly; `max_steps` is a required integer in 1–2 and `max_requests` in 1–6. The existing investigation timeout bounds the whole segment, including its single AI objective-interpretation call. Existing direct, interactive and task-file commands retain their contracts; adaptive execution accepts trusted-local direct input only.

```bash
./start.sh beescan investigate --adaptive --target https://authorized.example --task 'Investigate supported disclosures field=APP_TOKEN'
./start.sh beescan investigate --inspect CASE_ID
./start.sh beescan investigate --resume CASE_ID --task 'Continue supported disclosures field=APP_TOKEN'
```

The example origin grants no third-party authorization. The actual local OS operator/process context, `trusted_local_enabled`, module availability, current settings, exact destination and all existing provider/namespace/DNS/TLS guards remain mandatory. Inspection performs no target requests. Every resumed segment binds fresh local authority and resolves the destination again; prior expiry/permission is never inherited. Changed origin, destination, objective, requested field, scope constraints or dependency revision refuses continuation. Additional operator wording is interpreted again through the existing named AI profile but cannot change the stored Case identity or supply executable parameters.

BeeAgent obtains one governed GET `/` and authenticates its redacted source before requesting It12 signals and a decision. The AI receives only operator task text and proposes a bounded objective enum; it never receives HTTP bodies or chooses executable actions. BeeScan intersects objective, authenticated observations, catalog, Mission and actual declared availability. The host executes only the two existing family/capability pairs through the existing collect/capture/managed-egress implementation and reauthorizes before each request. Each family performs its own discovery; no WebResponseFacts or InvestigationIntent is relabeled across scenarios. A full discovery + framework comparison + diagnostic check uses at most six actual requests. A negative/inconclusive check can lead to another eligible check; exhaustion produces explicit limitations and guidance.

Case ID remains stable across at most eight explicitly requested segments. Each segment has a distinct parent run, each action retains its own domain run/context, and captures retain original child/request/response/evidence identities. Parent Case storage is `storage/runs/<case_id>/module-beescan/case.json`; action summaries live in their segment's `case_action_<family>.json`. Existing investigation artifacts remain available. `case_report.json` and `case_report.md` present completed checks, status, evidence, metrics, limitations and next actions without raw bodies or sensitive values.

A Case checkpoint is an allowlisted schema-1 envelope with a canonical SHA-256 integrity digest, bounded segments/decisions/outcomes, stable target/scope/Mission identity, pending/terminal flags and metrics. ArtifactAPI writes are fsynced, atomically published and read back. A no-follow, owner-checked directory lock prevents concurrent continuation. Fresh loading uses the existing bounded, private, owner-controlled AssessmentSnapshot mechanism and verifies action records, exact source/marker digests, original source bindings, sufficient evidence and closed/enforced/cleanup-verified lifecycle artifacts. A digest detects changed bytes; it is not a signature against a malicious trusted OS account. Source authenticity follows the existing trusted local operator/storage threat model. Same-account hostile mutation remains outside that boundary.

Only sufficient authenticated MATCH/NO_MATCH summaries can be restored for reuse. Missing, corrupted or insufficient source/action records refuse resume; an interrupted action is never represented as completed. After a controlled interruption with verified cleanup, a later explicit resume can recapture the unfinished check under new authority and budget. Abrupt process death leaves a pending checkpoint that refuses continuation rather than trusting partial work. Redacted artifacts cannot reconstruct raw HTTP responses or replay plaintext secret values. A completed MATCH is terminal and does not replay a secret.

Adaptive capture uses `adaptive-redacted-v1` before every source persistence: metadata-only facts, opaque identities and a run-private HMAC commitment; raw captures, links and excerpts are omitted. Live framework evidence remains transient for existing deterministic analysis. Sensitive diagnostic presentation uses the unchanged foreground, owner-matching, same-device TTY gate after verified cleanup and final publication. Redirected output, reports, Case artifacts and AI inputs contain no disclosed value.

Metrics record actual attempted requests, exactness, capture launches, elapsed segment time and actual AI calls, accumulated across segments. Necessary recapture consumes the fresh segment budget and cumulative metrics. Token/cost values are null with `usage_status=unavailable`; no usage is fabricated. NO_MATCH, INCONCLUSIVE, REFUSED, TIMEOUT and ERROR remain distinct and never establish target safety or human verification.

The paired local source is supported for development with the existing exact editable installation checks. It does not establish production dependency provenance. Keep the reviewed immutable Git gate and update it only after an actual reviewed It12 revision is available. No BeeSDK/BeeUI change or runtime dependency is required. Run `tests/test_beescan_adaptive.py` and `integration_tests/test_beescan_adaptive_lab.py`; the latter reuses the existing explicit pinned laboratory prerequisites and real HTTP/HTTPS containment, and substitutes only objective AI interpretation. Independent review and hosted CI remain delivery gates.

Resume checks the domain Case identity before target discovery. Completed work is reusable only with a recorded opaque action identity matching the currently indicated resource and request profile. Changed resources stop with `evidence_not_equivalent`; start a new authorized Case for fresh evidence. Older checkpoints without an action identity remain inspectable but cannot supply reusable outcomes. The final sensitive presentation gate revalidates the saved Case snapshot alongside the published result.
